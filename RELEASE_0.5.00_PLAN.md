# RELEASE 0.5.00 — ПЛАН РЕАЛИЗАЦИИ

Основано на `RELEASE_0.5.00_AUDIT.md`. Принципы: модульность, feature-flags,
старые конфиги работают, у каждой функции есть выключатель и откат, ничего не
имитируем. Реализация — поэтапно, не одним коммитом.

Легенда полей: **Файлы** · **Зависит от** · **Риски** · **Готово, когда** · **Тест**.

## P0 — критические баги и совместимость

### P0.1 Эквалайзер роняет громкость — ✅ СДЕЛАНО (этот релиз)
- Файлы: `src/eq.rs`.
- Суть: убран сквозной preamp (`pre`), на выходе — мягкий клиппер (линейно до
  85% FS, дальше плавное колено). Подъём полосы теперь реально делает громче.
- Готово: подъём +12 дБ даёт ~+12 дБ на полосе без падения общего уровня.
- Тест: `eq::tests::bands_boost_and_cut` обновлён и проходит.

### P0.2 Цвета Mini 2 (оранжевый → синий) — ✅ СДЕЛАНО (этот релиз)
- Файлы: `src/led.rs`.
- Суть: для платы `mini2` каналы red/blue в sysfs разведены наоборот —
  маппинг переставлен (`r→blue`, `b→red`), чтение/запись остались согласованы.
- Готово: оранжевый отображается оранжевым на Mini 2; Lite (`micro`) не задет.
- Тест: проверить на живой Mini 2 всю палитру (красный/оранжевый/жёлтый/синий).

### P0.3 «Что играет» после «стоп» — ✅ закрыто гейтом, доработок не требует
- Файлы: `src/alice.rs`.
- Суть: гейт `WhatPlaying => playing || airplay.is_active()` уже отдаёт вопрос
  Алисе, когда SoundCloud не играет, поэтому старый трек не называется.
- Ограничение (в README «Известные ограничения»): soundya не озвучивает трек
  Яндекс Музыки сам — он уступает Алисе.
- Тест: регресс-тест на гейт (SC stopped → WhatPlaying не наш).

### P0.4 Версия конфига + бэкап + миграция
- Файлы: `src/settings.rs`, `src/update.rs`.
- Зависит от: —. Делать **до** любых новых полей онбординга.
- Риски: порча пользовательского конфига при апгрейде.
- Готово: при старте новой версии старый `settings.json` читается без потерь,
  перед первой записью создаётся `settings.json.bak`, добавлено поле
  `schema_version`, неизвестные поля не теряются.
- Тест: юнит — загрузка конфига 0.4.x → сериализация → все старые значения на
  месте; интеграция — апгрейд на живой колонке не сбрасывает токен/сценарии.

## P1 — onboarding, SoundCloud, Яндекс Музыка, AirPlay

### P1.1 Чекбокс «Использовать Яндекс Музыку» (§11.1)
- Файлы: `src/settings.rs` (поле `yandex_music: bool`, default on), `src/alice.rs`
  (гейт), `src/web.html` (чекбокс в «Колонка»).
- Зависит от: P0.4.
- Риски: регресс маршрутизации. При выключенном чекбоксе soundya **не
  перехватывает** музыкальные команды с упоминанием Яндекса.
- Готово: выкл → `names_yandex`-команды и дефолтная музыка полностью у Алисы,
  soundya не вмешивается; вкл → текущее поведение.
- Тест: расширить `alice.rs` тесты обоими состояниями флага.

### P1.2 Распознавание «включи альбом» (§11.3)
- Файлы: `src/alice.rs` (`intent_core`, ветка `альбом`/`пластинку`).
- Риски: пересечение с плейлистами.
- Готово: «включи альбом X», «… исполнителя», «… в SoundCloud», «… в Яндексе»
  маршрутизируются верно; альбом не уходит в поиск плейлиста.
- Тест: таблица кейсов в `alice.rs` tests.

### P1.3 Таблица приоритетов интентов (§11.5)
- Файлы: `docs/` (таблица), `src/alice.rs` (привести гейт к таблице).
- Готово: документирован порядок разбора всех музыкальных интентов, гейт ему
  соответствует, конфликтов нет.
- Тест: по одному кейсу на строку таблицы.

### P1.4 SoundCloud: кнопка «Подключить» + детект протухания (§9)
- Файлы: `src/web.html`, `src/web.rs`, `src/sc.rs`.
- Риски: **ограничение** — полный OAuth refresh недоступен (закрытая регистрация
  client_id). Реализуем: кнопка открывает вход, забирает `oauth_token` без ручного
  копирования; при `token_bad` — уведомление и предложение переавторизоваться,
  прочие настройки не сбрасываются.
- Готово: пользователь подключает SoundCloud без ручного поиска токена; протухший
  токен не роняет остальной конфиг.
- Тест: юнит на `set_token`/`token_bad`; ручная проверка флоу.

### P1.5 AirPlay 2 — стабильность и честная подпись (§4)
- Файлы: `src/airplay.rs`, `scripts/build-shairport.sh`, `packaging/shairport-sync`.
- Риски: лаг/заикания; реально ли собран AirPlay 2.
- Готово: воспроизведение стабильно, задержка приемлема, устройство корректно
  обнаруживается, нет конфликта с голосом Алисы; в UI/README заявлена **ровно та**
  версия AirPlay, что реально собрана.
- Тест: ручная проверка с iOS/macOS; проверка строки версии из сборки shairport.

### P1.6 Onboarding: мастер + голосовая инструкция + DHCP-шаг (§2, §3)
- Файлы: `src/web.html` (мастер, карточки модулей, walkthrough), `src/update.rs`
  (запуск после установки), `src/alice.rs` (`say()` с авто-IP:порт).
- Зависит от: P0.4 (миграция/бэкап).
- Риски: не навязывать модули; работать на слабом железе; авто-IP может не
  определиться — всегда давать fallback по IP, домен `soundaya` опционально.
- Готово: после обновления колонка голосом называет адрес; мастер даёт включить
  **функции** (не «что ставить»), невключённые модули выключены и показывают
  короткий гайд; шаг про DHCP reservation есть.
- Тест: прогон первого запуска на колонке; проверка, что отказ от модуля
  оставляет его выключенным.

### P1.7 Праздничный баннер «100 пользователей» (§1)
- Файлы: `src/web.html` (баннер на главной), источник числа — stats-сервер
  (`/badge.json` / `/stats.json`), не хардкодить.
- Риски: баннер не должен тормозить слабые устройства.
- Готово: крупная анимированная цифра из живого источника, приглашение в Telegram,
  стиль как у анимированного задника, адаптивно на мобильных.
- Тест: офлайн-рендер (Playwright) на десктопе и в ширину телефона; проверка,
  что число берётся из сети, а не зашито.

## P2 — управление ПК/ТВ, Telegram, планировщик

### P2.1 Конструктор макросов TV (§6)
- Файлы: `src/tv.rs`, `src/adb.rs` (переиспользуются), новый слой сценариев
  (хранилище JSON в конфиге), `src/web.html` (визуальный редактор),
  `src/alice.rs`/`main.rs` (назначение голосовых команд → `Cmd`).
- Зависит от: P0.4.
- Риски: разные модели Android TV умеют разное; нет гарантии списка приложений.
- Готово: опрос установленных приложений (если устройство умеет; иначе — ручное
  добавление с объяснением); типы шагов из §6.3; создание/редактирование/
  переупорядочивание/задержки/тест шага/сохранение/назначение голоса. Функция
  считается готовой, только если реально отрабатывает на backend, а не рисуется.
- Тест: юниты на парсер/исполнитель сценария; ручной прогон на реальном TV.

### P2.2 Конструктор сценариев ПК (§7)
- Файлы: `src/pc.rs`, `pc/` (агент), `src/web.html`.
- Риски: безопасность — не допускать произвольного удалённого выполнения;
  подтверждение опасных действий; защищённый канал (токен уже есть).
- Готово: запуск/закрытие программ, файлы, URL, громкость, переключение
  аудиоустройств, последовательности, задержки, проверка процессов, условия;
  опасные действия требуют подтверждения.
- Тест: юниты на протокол агента; ручной прогон на Windows.

### P2.3 Telegram-интеграция (§8)
- Файлы: новый `src/telegram.rs`, `src/settings.rs`, `src/web.html`.
- Риски: несколько аккаунтов и MTProto — тяжело для бинарника; **возможно вынести
  в отдельный сервис/агент**. Сессии хранить безопасно, не в открытом виде.
- Готово: подключение аккаунтов, белый список важных контактов, голосовые
  уведомления (с лимитом длины, режимом тишины, защитой от повторов, возможностью
  не озвучивать содержимое), голосовая отправка с подтверждением текста.
- Тест: юниты на фильтры/белый список; ручная проверка уведомлений.

### P2.4 Планировщик (§10)
- Файлы: новый `src/planner.rs`, хранилище JSON, `src/web.html`,
  `src/alice.rs` (маршрут «какие планы», «добавь встречу», «напомни…»).
- Риски: не дублировать события при синке с Google Calendar; OAuth.
- Готово: свой календарь (CRUD, повторы, напоминания, приоритеты, категории,
  статусы); «Алиса, какие планы» идёт в **свой** планировщик; Google Calendar —
  опциональная двусторонняя синхронизация без дублей.
- Тест: юниты на повторы/напоминания; ручная проверка голосовых запросов и синка.

## P3 — Bluetooth, мультирум, Ambilight, автозапуск, бот-сообщество

### P3.1 Ambilight: новые эффекты + предпросмотр (§14)
- Файлы: `src/led.rs`, `src/vis.rs`, `src/web.html`.
- Риски: нагрузка на ARM — все анимации оптимизировать; не показывать параметры,
  недоступные модели.
- Готово: волна, радуга, дыхание, переливание, бегущий свет, реакция на музыку/
  голос, случайные переходы, пользовательские схемы; предпросмотр в UI; параметры
  адаптированы под число зон модели.
- Тест: юниты на генерацию кадров (как уже есть для `music_frame`); визуальная
  проверка на моделях.

### P3.2 Мультирум / единый аудиохаб (§12)
- Файлы: `src/airplay.rs`, `src/alsa.rs`, новый роутер источников, `src/web.html`.
- Риски: **идеальную синхронность не обещаем** без замеров задержек.
- Готово: переключение «колонка / браузер / ПК / одновременно»; когда музыка
  уходит на другое устройство, на колонке остаётся голос Алисы.
- Тест: ручная проверка сценариев из §12.2.

### P3.3 Bluetooth-выход на внешнюю колонку (§13)
- Файлы: новый `src/bluetooth.rs`, `src/alsa.rs`.
- Риски: **упирается в BT-стек прошивки и профиль A2DP source** — требует проверки
  на конкретной модели; если недоступно — описать ограничение, не имитировать.
- Готово (при технической возможности): музыка на внешней BT-колонке, голос и
  управление остаются на Станции; настройки подключения/выбора устройства.
- Тест: проверка A2DP source на целевой прошивке до заявления функции.

### P3.4 Автозапуск пользовательского конфига (§15)
- Файлы: `src/settings.rs`, `src/main.rs`, `src/update.rs`.
- Риски: восстановление после нештатной перезагрузки.
- Готово: выбор конфигурации автозапуска, поведение при перезагрузке, опц.
  задержка; применяется автоматически; состояние восстанавливается.
- Тест: перезагрузка колонки → конфиг применился сам.

### P3.5 Бот приёма в сообщество (§18)
- Файлы: новый сервис рядом со `server/` (Python, Telegram Bot API), **автономно
  от основного процесса**.
- Риски: юридически корректный текст соглашения (без заведомо недействительных
  отказов от ответственности); одноразовые invite-ссылки; логирование согласий.
- Готово: приветствие → дисклеймер → правила → явное «Соглашаюсь» → доступ;
  лог согласий (user id, дата/время, версия соглашения); повторное подтверждение
  при изменении условий; удаление неподтвердивших.
- Тест: прогон сценария входа; проверка, что доступ не выдаётся без согласия.

## Сквозные задачи (§17 аудит кода, §19 этапы)

- **Тесты:** музыкальная маршрутизация, состояния плеера, SoundCloud,
  сохранение/миграция конфига, макросы, автозапуск, Ambilight, Telegram-события.
  Регрессионные — обязательны. Существующие функции и публичные API не ломать.
- **После каждой крупной задачи:** запуск тестов, проверка логов, старых сценариев,
  совместимости со старыми конфигами, работы после перезагрузки.
- **Критерий «готово»:** функция работает на backend, а не только видна в UI.
- **Документация (§19 этап 5):** README, инструкции установки/обновления/первой
  настройки/модулей, список известных ограничений.

## Порядок работ

1. P0.4 (версия конфига/бэкап) — фундамент совместимости.
2. P1.1–P1.3 (Яндекс/альбомы/таблица интентов) — закрывают фидбек §11 малой кровью.
3. P1.6–P1.7 (onboarding, баннер) — лицо релиза.
4. P1.4–P1.5 (SoundCloud, AirPlay 2) — в достижимых границах.
5. P2 модулями по одному (TV → ПК → Telegram → планировщик), каждый за флагом.
6. P3 по готовности и после проверки платформенных ограничений.

Каждый модуль — свой `*_on` флаг; включение одного не ломает другие; у критичных
изменений — откат (бэкап конфига, прежняя версия через `update.rs`).
