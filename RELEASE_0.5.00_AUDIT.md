# RELEASE 0.5.00 — АУДИТ КОДОВОЙ БАЗЫ

Состояние на коммит `8f3c73c` (ветка master). Документ описывает **фактическое**
устройство проекта, а не желаемое. Цель — понять, что переиспользуется, что
дорабатывается, а что реально ограничено платформой.

---

## 1. Общая архитектура

soundya — один бинарник на Rust (edition 2021, `opt-level="z"`, `panic="abort"`,
~12.5k строк в `src/`), который ставится на рутованную Яндекс Станцию и работает
рядом со штатной Алисой. Зависимостей минимум: `ureq`, `serde`/`serde_json`,
`symphonia` (декод mp3/aac), `webpki-roots`. Никакого async-рантайма — всё на
обычных потоках и каналах `std::sync::mpsc`.

Точки входа и поток управления:

- **`main.rs` (2111 стр.)** — `Controller`: единый владелец состояния плеера
  (`flags`, `queue`, `pos`, `generation`), крутится в одном потоке и принимает
  `Cmd` из канала. Все действия (play/pause/next/seek/settings/pc/tv/bypass)
  сериализуются через этот канал — гонок по состоянию плеера нет by design.
- **`alice.rs` (1388 стр.)** — перехват голоса: слушает распознанные фразы,
  функции `intent()`/`intent_core()` превращают текст в `Intent`, гейт решает,
  забирает ли soundya команду себе или оставляет Алисе, и `cancel_alice()` гасит
  её штатный ответ. Здесь же `say()` через START_VOCALIZE.
- **`web.rs` + `web.html`** — панель на :8765. `web.html` вшит через
  `include_str!` (один файл, 105 КБ).
- **`settings.rs`** — конфиг (serde-struct, все поля `#[serde(default)]`),
  JSON на диске.
- Сервисные модули: `sc.rs` (SoundCloud API), `airplay.rs` (обёртка
  shairport-sync), `led.rs`/`vis.rs` (подсветка/визуализация), `eq.rs` (DSP),
  `alsa.rs`/`buffer.rs`/`player.rs` (звуковой тракт), `adb.rs`/`tv.rs`
  (Android TV), `pc.rs` (ПК-агент), `bypass.rs`/`zapret.rs`/`ipt.rs`/`mdns.rs`/
  `dns.rs` (обход блокировок), `update.rs` (самообновление), `volume.rs`,
  `luna.rs` (упаковка под Luna/YAM), `clock.rs`, `buttons.rs`, `history.rs`,
  `stats.rs`, `fsx.rs`.
- **`server/`** — отдельный Python-сервер статистики (195.209.211.30:8787),
  к основному бинарнику отношения не имеет, живёт сам по себе.

Вывод: архитектура **однопоточный владелец состояния + каналы** — здоровая,
масштабируется добавлением новых `Cmd`/`Intent` без риска для существующего.
Новые модули 0.5.00 должны встраиваться так же: как независимые источники `Cmd`
и как поля-флаги в `Settings`, а не как параллельные владельцы плеера.

## 3. Текущие проблемы и конфликты

1. **Голосовая маршрутизация музыки — самая хрупкая часть.** Вся логика «чьё
   это — наше или Алисы» живёт в одном гейте `alice.rs` (строки ~1078–1113) и в
   `intent_core()`. Любой новый источник (Bluetooth, мультирум, Яндекс-чекбокс)
   проходит через этот гейт. Риск регрессий здесь максимальный → менять только
   с тестами (они уже есть, надо расширять).
2. **`web.html` — один файл на 105 КБ, вшитый в бинарник.** Удобно для доставки,
   но любой новый модуль (onboarding, конструктор макросов, планировщик) раздувает
   его и усложняет диффы. Нужна внутренняя секционная структура, без дробления на
   внешние файлы (бинарник должен оставаться самодостаточным).
3. **Состояние «что играет».** soundya знает только своё состояние (SoundCloud +
   AirPlay). Гейт `WhatPlaying => playing || airplay.is_active()` уже корректно
   отдаёт вопрос Алисе, когда SoundCloud не играет, поэтому сценарий из §11.4
   (старый трек после «стоп») на уровне soundya закрыт. Ограничение: soundya
   **не может сам озвучивать трек Яндекс Музыки** — у него нет доступа к её
   плееру, он только уступает Алисе. Это надо честно отразить, а не имитировать.
4. **SoundCloud авторизация** держится на cookie `oauth_token`. Публичная
   регистрация OAuth-приложений у SoundCloud закрыта много лет — полноценный
   authorization-code + refresh недоступен без одобренного client_id. Это
   техническое ограничение, а не недоработка (см. §6).
5. **Нет версии конфига.** `Settings` полагается на `#[serde(default)]` —
   прямой миграции/бэкапа нет. Для безопасного апгрейда 0.4.x → 0.5.00 нужен
   номер схемы и резервная копия перед записью.
6. **Ресурсы.** Станции — слабое ARM-железо (armv7). Любые эффекты, агенты и
   опросы должны быть ленивыми и отключаемыми; async-рантайм тащить не стоит.

## 4. Что переиспользуется как есть

- Ядро `Controller` + каналы `Cmd` — фундамент для всех новых действий.
- `adb.rs`/`tv.rs` — готовая база под конструктор TV-макросов (добавляется слой
  сценариев поверх `shell()`/keyevent, без переписывания транспорта).
- `pc.rs` + PowerShell-агент — готовая база под ПК-сценарии.
- `airplay.rs` (shairport-sync) — база под AirPlay 2 и мультирум.
- `led.rs` — детект модели/зон уже есть, новые эффекты добавляются как режимы.
- `settings.rs` — расширяется новыми `#[serde(default)]`-полями без слома старых
  конфигов (каждый модуль — свой флаг `*_on`).
- `update.rs` — транспорт обновления; onboarding встраивается в его хвост.

## 5. Что требует переписывания/нового кода

- **Переписывать — ничего.** Ядро и транспорты здоровы.
- **Новый код (модулями):** onboarding+миграция, конструктор макросов (TV/ПК) и
  его хранилище сценариев, планировщик, Telegram-клиент, мультирум-роутер,
  Bluetooth-слой, новые эффекты Ambilight, OAuth-кнопка SoundCloud (в рамках
  ограничений), бот-сообщество (отдельный сервис рядом со `server/`).

## 6. Технически невозможное или ограниченное — честно

- **SoundCloud OAuth с refresh (§9):** публичная выдача client_id/secret у
  SoundCloud закрыта. Реально достижимо: кнопка «Подключить», которая открывает
  вход и забирает `oauth_token` из сессии (как сейчас, но без ручного копирования),
  + авто-детект протухшего токена и подсказка переавторизоваться. Полный
  refresh-token-флоу обещать нельзя, пока нет одобренного приложения.
- **AirPlay 2 (§4):** зависит от того, собран ли shairport-sync с поддержкой
  AirPlay 2 (нужны соответствующие зависимости и режим). Если в сборке реально
  только AirPlay 1 — так и писать, не выдавать за 2.
- **Bluetooth A2DP source (§13):** вывод звука Станции на внешнюю BT-колонку
  упирается в BT-стек прошивки и наличие профиля source. Требует проверки на
  конкретной модели; без подтверждения — не имитировать, описать ограничение.
- **Мультирум-синхронизация (§12):** без замера задержек протоколов идеальную
  синхронность не обещаем; реалистично — независимые выходы и переключение.
- **Google Calendar двусторонняя синхронизация (§10.2):** требует OAuth и
  аккуратной дедупликации; как опциональная надстройка поверх своего календаря.
- **Озвучивание содержимого Telegram (§8.3):** ограничено Telegram API и
  приватностью; делать по белому списку, с лимитом длины и возможностью отключить.

## 7. Зависимости, которые понадобится добавить

Оценивать осторожно (размер бинаря, ARM, `panic=abort`):

- Telegram-клиент: по возможности на `ureq` + Bot API (без тяжёлых крейтов);
  пользовательские аккаунты (MTProto) — отдельный вопрос, возможно отдельный
  сервис, а не в бинарнике.
- Планировщик/календарь: своё хранилище JSON + `ureq` для Google (OAuth).
- Остальное (макросы, эффекты, onboarding, мультирум) реализуемо на текущем
  стеке без новых зависимостей.

## 8. Итог аудита

Проект в хорошем состоянии: единое ядро, минимум зависимостей, многие «новые»
пункты 0.5.00 уже имеют рабочий фундамент (AirPlay/shairport, ADB/TV, ПК-агент,
Яндекс-роутинг). Два критических бага релиза (эквалайзер, цвета Mini 2) уже
исправлены. Основные риски — голосовая маршрутизация и отсутствие версии конфига;
оба закрываются аккуратно и с тестами. Часть пунктов (SoundCloud OAuth, AirPlay 2,
Bluetooth, мультирум) ограничена внешними факторами — их реализуем в достижимом
объёме и честно документируем границы. План — в `RELEASE_0.5.00_PLAN.md`.
